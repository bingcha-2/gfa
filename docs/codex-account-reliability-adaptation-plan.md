# GFA 账号可靠性与模型质量优化方案

日期：2026-09-21。初版结合 Sub2API STATE Kit、官方 Codex 源码和 GFA 代码整理方案；用户随后要求实施第一批三项，落实情况如下。以下验证记录截至本地验收；验收时未提交或部署，没有调用真实母号或修改生产配置。“已有”指代码已具备，实际发布以提交和部署记录为准。


## 第一批实施与本地验收结果（2026-09-21）

- **刷新协调已实现：** 默认 Codex provider、管理端额度及权益查询共用按账号/凭据代次的刷新任务；正常查询复用有效 token。明确的上游 401 最多触发一次协调刷新及只读请求重试，403、429、网络错误不触发令牌轮换。重置卡消费不自动重放。
- **写回竞争已修复：** 刷新结果先按凭据代次比较并同步持久化；重新授权、导入生成新代次。租约层不再整对象写回旧账号，非凭据状态使用字段级 CAS 补丁合并；旧补丁不能恢复删除的账号或覆盖新授权。新租约及其签名证明携带凭据摘要，迟到 401 只能清除当时被拒绝的凭据。缺少代次证据的外部报告不直接清令牌。
- **账号复核暂停已实现：** HTTP JSON、SSE、WS 中受限枚举的明确停用/验证错误，经过租约关联校验后进入持久化待复核状态，记录客户端报告来源及时间；不将客户端报告当作已确认封禁，不更改 enabled。冷却到期、成功报告、刷新令牌和普通错误不会解除，管理员显式恢复后旧租约报告不能再次暂停。普通 HTML 403 或模糊权限错误不按封禁处理。Codex 新旧报告及绑定账号统一有限 429 退避。
- **服务端脱敏已实现：** 请求头、原因文本、封禁证据及历史记录查询/支持包导出复用过滤器。覆盖大小写、嵌套对象、常见 STATE 与凭据别名、URL/form 参数；解析有大小和深度边界。历史库不做全表重写，读取时兜底过滤。
- **写盘失败保护：** 保留线上已有的定时写盘捕获与 60 秒重试；仅写入成功后清除 dirty 状态，对应失败恢复测试随本批纳入版本管理。
- **资源边界：** 没有增加插件进程、Redis、数据库表或定时上游模型请求。健康缓存令牌租约不新增账号文件写入；刷新协调只覆盖同一服务进程。磁盘写入失败时轮换结果仅保留在有界进程内存，重试先保存而不重复 OAuth；进程退出前若仍无法写盘，不能保证恢复这些未持久化凭据。
- **验证方式：** 全部使用临时账号文件、模拟上游和数据库 mock；覆盖 Windows UTF-8 BOM、跨入口并发、重新授权、迟到报告、跨重启暂停、脱敏和历史导出。本轮未验证真实账号恢复，也未进行生产压测。

验证结果：28 个相关测试文件首轮 362 项通过；最后补充损坏账号文件的两项回归后，对应两文件 25 项全部通过，累计覆盖 364 项不同测试。服务端 TypeScript 检查和差异检查通过。验证过程发现本机 C 盘已满，最终使用 D 盘临时目录完成；未清理用户数据。

下文保留实施前的代码快照、原始设计和分阶段安排；P0 已按上文完成，旧缺口描述仅解释实施动机，P1 项目仍未实施。
## 结论

优先借鉴任务去重、版本校验、账号隔离、失败停止和结果可验证这几项工程设计。先减少重复刷新、错误重试、状态串扰及上下文损失，再评估回答质量。

目前没有证据证明 STATE 注入能防止账号封禁，也没有证据把 GFA 的封禁归因于某一处代码。母号 32 的最小请求已经出现“292 字节 STATE + invalid_prompt”；不能把长度当成恢复成功，更不能把它当成解除账号限制的方法。

## STATE 策略需要修正的地方

[原文章](https://blog.caowo.de/posts/chatgpt-codex-292-state-anti-degradation-2026/)把 STATE 注入与调度变化联系起来，但其“通行证”“撤销”等解释没有形成可依赖的官方协议。

[官方 Codex client.rs](https://github.com/openai/codex/blob/main/codex-rs/core/src/client.rs)明确要求 `x-codex-turn-state` 在同一轮内保持，下一轮创建新状态；跨轮复用会违反客户端与服务端约定，并可能造成路由错误。

据此调整 GFA 方案：

- 正常透传客户端在当前轮使用的状态，核对 HTTP/WS 的生命周期；不自行从历史请求提取状态再注入新轮。
- 会话账号亲和与轮内状态分别管理。一次用户轮次可能包含多次工具调用和多个 response ID；不能把会话、WS 连接、response ID 任意一个直接当成轮次边界。
- 客户端无法提供可靠轮次边界时，只透传及观察，不由代理推测后复用。账号切换不得携带旧账号状态；历史 `encrypted_content` 的格式合法不代表新账号可解密。
- 292/332 是外部实现的长度规则；312 的解释和约一小时有效期属于社区策略。GFA 不用这些数字判定账号健康。
- 暂不引入动态出口采集、跨会话票据共享或自动持续补票。它们既不能解释母号 32 的失败，又会增加请求和维护成本。

这部分取代旧《兼容性修复与 STATE 借鉴方案》中尚未实施的账号级状态协调器建议，已完成的协议与诊断修复继续保留。

## GFA 已有的基础

此前 `1a16df43`、`848cd289` 已提交并推送的相关代码包括：

- 保留上游模型字段和推理强度，工具/状态请求不再静默丢失；不把失败或断流包装为完成。
- HTTP/WS 结构化诊断，区分请求模型、发送模型、上游模型及完成状态；记录经过限制的错误码和请求标识。
- 会话账号亲和、异步刷新前预留、部分有状态请求的固定出口保护。
- `invalid_prompt`、上下文错误及模型字符串不一致不触发自动换号；容量和限流有限冷却。
- 有界健康摘要、按需分页；近期封禁证据缓冲和批量请求日志。

尚未解决：上游拒绝的根因、完整轮次状态生命周期、跨入口刷新竞争、真实账号推理并发限制以及回答质量的量化对照。

## 实施优先级

### P0-1：统一母号令牌刷新

**代码证据：** `apps/server/src/leasing/remote-codex/auth/codex-token-provider.ts:21` 没有并发合并；`apps/server/src/leasing/rosetta/codex.service.ts:500` 的额度查询先清空 access token 再刷新。租号等入口也调用刷新函数。

**建议改法：**

1. 建立统一刷新入口。同账号、同凭据代次只允许一个刷新请求，其余调用等待同一结果；不只按 JavaScript 对象引用去重，因为调用方可能各自读取账号副本。
2. 正常查额度复用仍有效的 token。确认 401 后允许一次协调刷新，不将所有查询都变成强制刷新。
3. 刷新结果写回前比较账号身份和凭据版本，防止旧结果覆盖重新登录后的授权；只更新凭据字段，避免旧账号数组覆盖别的配置变更。
4. 轮换后的凭据通过现有存储入口及时持久化；写入失败明确报错和保留可恢复状态，不依赖稍后某次额度查询成功才保存。

可参考 GFA 已有 `remote-anthropic/auth/claude-token-provider.ts` 的 `inFlightRefresh`，仍需补齐 Codex 的跨对象及写回版本保护。这是借鉴协调模式，不是声称 STATE Kit 自身替宿主管理 OAuth 刷新。

**验收：** 并发租号和额度查询只发一次刷新；重新授权发生在刷新中途时旧结果不落盘；失败后锁释放；持久化失败可见。先用本地模拟上游验证，不需要消耗母号额度。

**成本：** 少量在途 Promise 和版本字段；减少重复网络请求。单进程锁只覆盖单服务实例，多实例部署需使用现有共享存储的原子协调。

### P0-2：明确停用、需验证与临时错误分开处理

**代码证据：** `lease-service.ts:3331` 的永久错误分支限定 HTTP 400/403，`:3342` 的验证分支限定 HTTP 403；`codex-health.ts:48` 对其他失败归入上游错误。静态路径显示，HTTP 200 流内的 `account_deactivated` 可能只进入单模型短冷却。此处还没有测试复现，不能表述为已在线发生。

**建议改法：**

- 对受限枚举中的明确停用/验证错误，统一解析 HTTP JSON、SSE 和 WS 终态，不依赖外层 HTTP 状态。
- 客户端报告必须继续校验租约归属。签名租约只证明账号关联，并不证明客户端报告一定真实；疑似报告可暂停并待管理员核验，不能据任意文本永久修改账号配置。
- 将“已确认停用/需人工验证”与“限流/容量冷却”拆开。前者停止自动维护并等待复核恢复，后者按 Retry-After 自动恢复。
- 审查 `cleanupExpiredBlocks` 当前到时清零的行为，使明确停用不因普通冷却到期重新进池。保留原始原因和首次/末次时间。
- 统一旧客户端及后台维护的退避。现有 `codex.provider.ts` 的 `rateLimitZeroCooldown` 和绑定账号兼容分支需要一起核对，避免新旧链路相互抵消。

停止新分配不等于撤销已经发给客户端的上游 token；旧客户端仍持有的有效凭据是独立边界，不能宣称服务端标记停用后所有在途请求都会立即停止。

**验收：** HTTP 200 + 明确停用码与 HTTP 403 的分类一致；普通 HTML 403 不标成封号；旧成功不能解除新停用；429 到时能恢复；恢复账号有明确操作和记录。

**成本：** 少量状态字段和状态变更写入，无新增定时探测。

### P0-3：补服务端日志脱敏

**代码证据：** 新客户端已经过滤 STATE，但 `token-server/request-log-tracker.ts:32` 的服务端敏感头过滤表还没有 `x-codex-turn-state`。旧客户端或其他提交来源不能完全依赖客户端过滤。

**建议改法：** 服务端对 STATE、凭据及已知同义字段统一过滤，封禁快照复用同一规则；诊断只保留长度、是否出现及必要的脱敏关联值。

**验收：** 大小写及嵌套头对象均不会留下原文；请求日志、封禁快照和导出入口一起核对。

**成本：** 复用现有日志处理，不增加存储量。

### P1-1：限制真实推理并发

**代码证据：** `token-server/lease-scheduler.ts:330` 对活动租约数量做评分；`lease-service.ts:3409` 明确客户端可重复使用租约。租约少不代表同时生成请求少，当前这些代码不能证明存在账号级硬并发上限。

**建议改法：** 先统计实际在途生成，再增加按账号的许可。GFA 的生成发生在各客户端，服务端下发包含上游 token 的租约，所以跨设备协调需要每次生成的轻量许可协议，不能只改调度评分。它只约束接入协议的已升级客户端；所有生成入口和客户端版本都需要覆盖，旧客户端或直接持 token 请求上游的流量仍可能绕过。

- HTTP 生成、WS 多轮、取消、断线和客户端崩溃均有许可回收规则；许可带期限，并为长轮次设计续期或受控超时，避免过早释放导致超卖。
- 等待有界，忙时返回明确 Retry-After；不把请求无限堆进服务器内存，也不因一次拥堵自动更换会话账号。
- 有子代理需求时统计其实际生成，而非把一个用户操作永远当成一个请求。限制值先观察后配置，不把 1、2 等任意数字称为官方安全阈值。
- 先单账号开启。母号 32 当前拒绝最小请求，适合保留故障证据，暂不能承担吞吐或质量基线；恢复后再验证。

**验收：** 参与协议的已升级客户端在多设备复用同一租约时仍共同受限；取消/断线不泄漏许可；重复释放无副作用；长轮次不因过早到期超卖。

**成本：** 中等。新增控制面往返和有界内存计数，必须测量后再扩大；第一阶段不必为此部署独立 Redis 或插件进程。若要求服务端不可绕过的硬上限，需由服务端控制生成转发链路，或有上游提供的受限凭据机制；这属于更大的架构改动，不计入本方案第一阶段。

### P1-2：补齐出口与上下文连续性

**代码证据：** `apps/app/codex_egress.go:81` 的强制出口保护依赖会话标识等条件；`:124` 仍保留兼容回退。已观察到账号切换时会清除 STATE，但这不等于覆盖所有轮次、历史状态和旧客户端。

**建议改法：** 统一审核刷新、额度查询、生成 HTTP、WS 的路线策略；管理员指定固定路线时，一致报告路线不可用，避免隐式切换。轮内 STATE 按官方语义透传；切换账号后遇到不可迁移历史，明确提示建立新会话或使用可迁移的明文摘要，不悄悄删除工具结果和历史后继续宣称上下文完整。

**验收：** 指定代理失败时没有未声明的出口回退；同轮状态保留、不同轮不由代理注入旧状态；账号变化不会把旧账号状态带给新账号；正常工具历史不丢失。

**成本：** 低到中，主要是客户端协议覆盖；无必要按请求查询公网 IP。

### P1-3：做轻量异常证据页与质量对照

复用现有每母号近期请求缓冲、封禁快照和请求日志批写。页面按需读取，不另外建设全量遥测系统。

展示：账号异常分类、完成状态、请求/发送/实际模型、推理强度、请求标识、发生时间、恢复条件，以及“上游明确返回 / 客户端报告 / 尚未确认”的证据来源。实际模型缺失显示“未知”，不能填请求模型代替。

借鉴外部项目的逐账号手动测试、取消、防重复操作和旧结果隔离。管理员打开页面或点预设题目不自动发送模型请求。需要诊断时显示使用母号额度，限制次数，失败保留证据；持续 `invalid_prompt`、明确停用或验证要求时停止自动试探。

回答质量采用固定任务与评分：算术只用于连通检查；代码任务以测试通过率、指令遵循和上下文保持为主。固定账号、出口、模型、effort 和上下文，交错进行小样本对照，分别统计生成成功率、错误分布、模型字段匹配率、任务正确率及延迟。单条长回答、推理 token 或模型名称均不足以证明能力提升。

**成本：** 按需查询和少量人工测试；不增加每号定时生成。现有日志仍按原保留期和批写规则运行，避免对旧大表做持续全量扫描。

## 错误对应的处理动作

| 证据 | 分类与动作 |
| --- | --- |
| 有效 token 的请求返回 401 | 鉴权失效；一次协调刷新，仍失败则停止并提示重新授权 |
| 明确的账号停用码或官方停用通知 | 停止该账号的新分配及自动维护；保留证据，复核后恢复 |
| 明确要求验证 | 等账号所有者完成官方验证；不靠重复请求等待自动恢复 |
| HTML 403 且有挑战标识 | 网站/网络验证挑战；单独记录接口与路线，不能直接判成封号 |
| 429 / capacity / overload | 区分额度和临时容量，有限退避；同会话优先等待 |
| invalid_prompt | 保留实际错误；普通业务不自动换号试探；可做一次受控最小对照，持续失败则停止 |
| completed，但模型字段不一致 | 路由观察异常；核对别名及配置，不当成封号证据 |
| completed，模型相同但任务失败 | 质量或上下文问题；用固定任务评分定位，不能仅靠模型字段判断 |

## 母号 32 与后续执行顺序

母号 32 已做的对照见 [基线记录](codex-account32-state-baseline.md)：GFA 最小请求和隔离官方 CLI 路径均失败。CLI 使用显式 provider，没有重新完成完整官方登录流程；账号和绑定出口也是共同变量，因此尚不能确定根因或排除出口因素。

推荐顺序：

1. 完成 P0 的刷新协调、错误分类回归及服务端脱敏。本地模拟验证即可，不再重复打母号 32。
2. 核对已推送修复的服务端部署与客户端版本，完成对应发布后再观察生产数据；提交代码不等于用户已获得修复。
3. 先用被动日志比较刷新次数、401/403/429/invalid_prompt 分布、明确停用事件和上下文错误；记录样本量，不能把一次短期下降归因于“防封成功”。
4. 账号恢复后再做有上限的单账号诊断；并发许可和质量评测随后小范围启用。每次只改变一个因素，保留关闭开关和配置版本。

第一阶段主要减少多余请求，预期服务器开销较小；这是按实现方式判断，尚无新增功能的性能实测。真实并发许可属于后续较大改动，不能承诺零开销。此次整理没有启动后台采集、安装插件、自动换出口或发布任何代码。
